# Game command undo and redo

## Problem and design reasoning

Authoring tools often apply an edit to several objects, update derived state, and notify other tools. If history captures a single property write or every pointer sample independently, a user can undo half a logical action or wade through many indistinguishable history entries. *Dreams* documents undo and redo for assembly edits and gives feedback identifying the reversed action. Media Molecule's GDC presentation describes using research and feedback to make the broader creation toolset approachable. Grouping edits by user intent is a design inference from that workflow. [Dreams Play & Edit walkthrough](https://docs.indreams.me/en-US/create/resources/mm-creator-content/templates/ancient-dangers/help/play-n-edit-walkthrough-2) · [Media Molecule, Expanding the Dreamiverse, GDC](https://www.gdcvault.com/play/1027293/UX-Summit-Expanding-the-Dreamiverse)

Epic's *Fortnite* editor exposes an undo history. One release note records fixes for crashes when deleting material expressions and undoing or redoing changes while a dependent material was open. This illustrates the need to preserve references and update dependent views when replaying an edit. [UEFN interface reference](https://dev.epicgames.com/documentation/fortnite/user-interface-reference-for-unreal-editor-for-fortnite) · [UEFN 33.00 release notes](https://dev.epicgames.com/documentation/en-us/fortnite/33-00-fortnite-ecosystem-updates-and-release-notes-in-creative-and-unreal-editor-for-fortnite)

## Techniques and practical checks

- **Record one action per user intent.** Preview drag updates interactively, capture the initial state once, and commit the final state as one history entry. Cancel restores the preview baseline without advancing history. **Check** that a long drag undoes in one step and that cancelling a second drag preserves the earlier undo and redo entries.
- **Store enough information to invert the operation.** Use stable object IDs and immutable before-and-after data for properties and references. Bundle dependent edits into the same command and define which derived data can be rebuilt after restoration. **Check** delete a parent with attached objects and referenced editor data, then undo and redo several times while dependent views are open. Compare those views and canonical authored state at both ends.
- **Define history branching and invalidation.** Creating an ordinary edit after undo replaces the abandoned redo branch unless the tool explicitly supports branches. For collaborative editing, validate the target revision or define a conflict policy before reversing an edit that others may have changed. **Check** undo, make a different edit, and attempt redo. In a shared session, also modify the same property from a second client and verify that history follows the stated conflict policy.
- **Bound history by cost and scope.** Coalesce compatible operations, budget history by memory, and publish a clear limit on how far the user can go back. Define whether scene changes, closing the editor, or restoring a saved version end the history scope. **Check** make repeated large edits until the budget is reached. Verify the advertised oldest undo point, history labels, and the ability to save and reopen a valid scene.
