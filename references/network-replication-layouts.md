# Network replication layouts

## Problem and design reasoning

A replicated object can contain far more state than another player needs to render or interact with it. Sending a raw memory image also ties the protocol to compiler layout and includes fields with incompatible lifetimes. In Valve's shipped Team Fortress 2 code, send tables separate local-player weapon data and use explicit property encodings. Blizzard's Dan Reed explains how Overwatch automates prediction and replication for scripted gameplay. An implementation inference is to define a replication layout around the consumers of each field, then verify the encoded result against gameplay tolerances. [Valve, Team Fortress 2 weapon send tables](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/shared/tf/tf_weaponbase.cpp) · [Blizzard, Networking Scripted Weapons and Abilities in Overwatch, GDC 2017](https://media.gdcvault.com/gdc2017/Presentations/Reed_Dan_NetworkingScriptedWeapons.pdf)

## Techniques and practical checks

- **Describe the wire representation explicitly.** Specify field identity, range, precision, recipient eligibility, and default value. Use bounded quantization where its error fits the feature. Keep runtime pointer layout independent of the wire format. **Check** minimum, maximum, and out-of-range values, along with a stationary and moving fixture. Compare decoded values and visible error against the chosen tolerances.
- **Delta against a known baseline.** Associate a delta with the baseline the receiver can actually reconstruct. Retain enough history for the intended network conditions and provide a complete-state recovery path when that baseline is unavailable. **Check** packet loss, reordering, late joins, and baseline eviction. Verify recovery reaches the authoritative state without applying a delta to the wrong object generation.
- **Group fields that must become visible together.** Capture related state at one simulation boundary and apply it before presenting dependent UI or effects. Treat one-shot event delivery separately where repeated snapshots could replay the same action. **Check** a loadout switch, health change, and ability-state transition under delayed snapshots. Confirm the client never presents combinations the server could not have produced.
- **Budget by change frequency and audience.** Capture bytes by field group, entity class, and recipient population. Prioritize state needed for immediate interaction and lower the frequency of tolerable background updates. **Check** a quiet scene, a dense encounter, and rapid relevance changes. Measure bandwidth and state age together and verify that lower-priority updates do not starve indefinitely.
