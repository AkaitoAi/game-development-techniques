# Runtime spatial indexing

## Problem and design reasoning

Checking every entity for every overlap, proximity trigger, and interaction spends time on objects that could never match. In shipped *Quake* code, id Software links entities into an area tree and traverses candidate branches before detailed collision tests. The code also treats an entity crossing a split differently from one fitting wholly on one side. At GDC 2013, IO Interactive and Moon Collider used *Hitman: Absolution* and other projects to explain why dynamic environments made extensive manual placement of tactical information brittle. The transferable inference is that the indexing structure should follow the queries, density, and movement patterns of the live world. An index narrows candidates, while the feature still owns its exact eligibility test. [id Software, Quake world and clipping code](https://github.com/id-Software/Quake/blob/master/WinQuake/world.c) · [Mika Vehkala and Matthew Jack, Spaces in the Sandbox, GDC 2013](https://gdcvault.com/play/1018038/Spaces-in-the-Sandbox-Tactical)

## Techniques and practical checks

- **Instrument the workload before choosing a structure.** A uniform or hashed grid fits similarly sized moving objects with local queries. A bounds tree can handle mixed object sizes and sparse regions more efficiently when the cost of maintaining it is acceptable. Keep a linear scan as a test oracle. **Check** uniform, clustered, and sparse scenes. Record candidates per query, update count, worst-query time, and total frame cost for the same query mix.
- **Make membership conservative.** Index bounds rather than centers when queries must see objects extending across boundaries. For a multi-cell grid, deduplicate candidates by stable identity and run the exact shape, distance, and layer filters afterward. **Check** large objects crossing multiple cells, touching bounds, negative coordinates, and rays grazing cell edges against the oracle. Verify no misses and one result per matching entity.
- **Publish updates at a defined phase.** Apply spawn, movement, despawn, and cell unload consistently before the queries that depend on them. Use a read snapshot or enforce a no-mutation phase when queries run concurrently. **Check** a teleport across many cells, immediate destruction and slot reuse, and a query during streaming. Verify the declared visibility rules and that stale handles do not resolve to replacement objects.
- **Separate persistent world coordinates from index coordinates.** Derive the index cell coordinate from the current origin and define how origin shifts remap entries. If results affect observable choices, apply an explicit tie-break by stable identity. **Check** the same query before and after an origin shift and with randomized insertion order. Compare exact results and confirm deterministic first-choice selection where required.
