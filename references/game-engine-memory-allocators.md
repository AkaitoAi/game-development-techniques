# Game engine memory allocators

## Problem and design reasoning

Gameplay often mixes short-lived scratch buffers, objects with stable footprints, and assets that live across levels. When all allocations take one path, contention, fragmentation, or expensive teardown may cause stalls even if live bytes look acceptable. The shipped *Quake* zone code combines independently freed blocks, mark-based hunk allocation, and cache behavior. At GDC 2015, Naughty Dog presented the allocation patterns used alongside frame-centric work and fiber jobs to help *The Last of Us Remastered* run at 60 fps. A transferable inference is to choose an allocator from measured lifetime, size, alignment, and ownership patterns, then observe its effect on tail latency and capacity. ## Techniques and practical checks

- **Use arenas for a shared lifetime.** Allocate frame or job scratch space linearly, then reset it once all CPU and GPU consumers are finished. Give persistent data a separate owner. **Check** by delaying a worker and GPU consumer past the normal frame boundary. Verify the arena is not reset early, and flag any retained scratch pointer before reuse.
- **Use pools for measured size classes.** Reuse slots for hot, similarly sized objects and put irregular or large allocations on a path suited to variable sizes. Include alignment and occupancy waste in the budget. **Check** long spawn and despawn bursts with mixed request sizes. Record live versus reserved bytes, high-water marks, and percentiles for allocation time.
- **Make ownership and failure explicit.** Carry the allocator or owning context to destruction when objects cross subsystem or worker boundaries. Define a bounded fallback, degradation path, or clean failure for each full pool. **Check** wrong-owner release in a diagnostic build, a cross-worker release, and a deliberately exhausted pool. Confirm the program catches contract violations and the supported pressure path does not corrupt live state.
- **Rehearse mixed lifetimes on target hardware.** Log requests by category, size, and lifetime. Measure both allocator overhead and usable capacity after realistic loading and unloading, including the largest request that must still succeed. **Check** repeated level transitions interspersed with long-lived assets and short-lived bursts. Compare frame-time tails, high-water marks, and capacity against the baseline allocator.
