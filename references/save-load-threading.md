# Save and load threading

## Problem and design reasoning

Moving file writes to a worker can leave snapshot capture on the critical frame and can introduce races if serialization keeps reading live gameplay objects. Wube documents that Factorio's background saving on macOS and Linux forks the process, allowing the parent to continue while the child saves. This uses platform process semantics to separate the save view, with additional memory cost and edge cases reported by the developer. It demonstrates a particular isolation strategy, rather than a portable prescription for every game. [Wube, Friday Facts 408](https://www.factorio.com/blog/post/fff-408)

Chris Butcher's GDC 2015 talk describes the lifetime and threading assumptions shared by Destiny's core systems. The portable recommendation below applies that engineering concern to saves. Give capture, encoding, I/O, reconstruction, and publication explicit owners and boundaries. It is an implementation inference, not a claim that Bungie used this save pipeline. [Bungie, Lessons from the Core Engine Architecture of Destiny, GDC 2015](https://media.gdcvault.com/gdc2015/presentations/Butcher_DestinyEngine_GDC2015_final.pdf)

## Techniques and practical checks

- **Split capture from encoding.** At a legal simulation boundary, copy a coherent generation into owned snapshot data. Let workers encode and compress that data without dereferencing mutable world objects. If capture is incremental, use a validated snapshot mechanism that keeps the generation consistent. **Check** mutate inventory, currency, and object ownership while a deliberately slowed encoder runs. Load the result and verify the saved invariants and generation. Measure capture pause separately from total save time.
- **Bound in-flight work.** Give requests a slot, generation, and terminal result. Budget snapshot buffers and compression scratch space. Coalesce only requests whose semantics permit a newer snapshot to replace the queued one. **Check** repeatedly request autosave and manual save under slow storage. Verify peak memory, queue length, and completion order remain within declared limits and every accepted manual request gets an outcome.
- **Restore off-thread data before publishing world state.** Decode and validate into staging data on workers, then perform engine-affine object creation, reference resolution, and service registration on their required threads. Release player control only when the restored world is ready. **Check** delay each phase and include a missing required asset or unsupported record. Confirm the old playable state or an explicit loading state remains valid until the replacement succeeds.
- **Make shutdown wait rules explicit.** A worker owns its buffers until completion. Cancellation can prevent future publication while an underlying platform write finishes. Keep the completion queue alive until outstanding operations have retired, or use an ownership object that outlives the scene. **Check** quit to menu, start another load, and terminate the session while capture, encoding, I/O, and restoration are each active. Verify no callbacks access destroyed state and the UI reports the actual outcome.
