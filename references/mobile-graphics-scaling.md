# Mobile graphics scaling

## Problem and design reasoning

A mobile graphics preset must account for differences among system-on-chip designs, graphics drivers, memory limits, and display resolutions. A preset can hit its target in one scene and lose frame consistency during a dense effect or camera transition. A single quality slider can also lower detail that players need while leaving the expensive subsystem untouched. Define a stable set of rendering features for each device tier, then use bounded runtime adjustments for scene-level load.

Epic and Samsung’s GDC session frames the Android port of *Fortnite* as a combination of graphics API work, memory tradeoffs, and content changes. The engineering takeaway is an inference from that scope: investigate quality, content, and backend costs independently when a device misses its budget. [Bringing Fortnite to Mobile with Vulkan and OpenGL ES, GDC 2019](https://www.gdcvault.com/play/1026128/Bringing-Fortnite-to-Mobile-with)

## Shipped examples and conference evidence

- **Fortnite Battle Royale on Android.** Epic and Samsung described optimizing Vulkan and OpenGL ES paths for mobile hardware and refining the Vulkan implementation across multiple mobile chip designs. The talk links the port to differences in API implementations and resource constraints. It does not establish one universal choice of backend for every game. [Epic and Samsung, GDC 2019](https://www.gdcvault.com/play/1026128/Bringing-Fortnite-to-Mobile-with)
- **Diablo Immortal on Android.** Google documents the team’s adaptation of a reflection denoiser for the game’s renderer and the performance limits of mobile ray-traced reflections. This is a concrete example of treating an advanced visual feature as a budgeted rendering path. [Android Developers’ Diablo Immortal case study](https://developer.android.com/stories/games/diablo-raytracing)
- **Dynamic resolution technique.** Apple’s developer session describes adjusting render resolution as scene complexity changes and discusses reconstruction. The design below applies that principle with measured bounds and an explicit readability floor. [Go further with Metal 4 games, WWDC25](https://developer.apple.com/videos/play/wwdc2025/211/)

## Practical techniques and checks

1. **Separate capability selection from quality selection.** Choose supported formats, shader features, and graphics backend from verified device capabilities. Choose scene quality through a separate tier for render scale, shadows, particles, reflection method, and texture residency. Define a baseline look that preserves silhouettes, hazards, aim cues, and readable text. **Check** boot production builds across representative GPU and driver families. Verify the selected path and run one captured scene per tier to confirm that missing features have intentional visual fallbacks.
2. **Scale the cost that limits the frame.** Measure CPU and GPU duration separately. Dynamic resolution primarily targets pixel-dependent GPU work. Submission-heavy scenes can instead need fewer objects, passes, or state changes. Define a frame-time budget from the target frame rate and leave headroom for effects and input responsiveness. **Check** sweep render scale through the allowed range in a shader-heavy view and a draw-heavy view. Compare percentile frame times and resource use, then keep only controls that improve the intended bottleneck.
3. **Bound and stabilize runtime changes.** Filter timing samples, use separate thresholds for degrading and recovering quality, and limit adjustment frequency. Keep interface rendering at an appropriate resolution and bound the size of any step visible to the player. Reset or rescale temporal history according to the reconstruction method when switching resolution. **Check** alternate dense effects and simple views while recording frame time and scale. Verify controlled recovery, stable text, and acceptable motion reconstruction during transitions and camera cuts.
4. **Budget memory for peak quality and transitions.** Include render targets, transient buffers, shader variants, and temporary coexistence while switching tiers. Keep fallback assets and shader paths available where the chosen feature can be disabled during a session. **Check** repeatedly enter the most expensive area, change quality, and return after backgrounding. Verify peak memory, visual continuity, and frame-time recovery on the lowest supported memory tier.
