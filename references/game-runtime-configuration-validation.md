# Game runtime configuration validation

## Problem and design reasoning

A configuration value can be well-formed while violating a runtime assumption. A worker count of zero, a timeout shorter than a retry interval, or a gameplay setting changed on only one peer can break a running session. Factorio separates startup settings, global runtime settings, and per-player settings. Its runtime API also describes the lifetime of player-specific setting tables. The shipped game's contract makes scope and change timing explicit. [Wube, Factorio LuaSettings](https://lua-api.factorio.com/latest/classes/LuaSettings.html) · [Wube, Factorio data lifecycle](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html)

Brandon Moro's GDC 2018 presentation describes how Destiny 2's asset pipeline evolved to support scalable iteration and shipping content. That is pipeline evidence about keeping data production usable as dependencies grow. Applying explicit constraints, provenance, and atomic publication to runtime settings is a design inference. These checks belong at the configuration boundary so every consumer receives a valid resolved configuration. [Bungie, Asset Pipeline: Destiny 2 and Beyond, GDC 2018](https://www.gdcvault.com/play/1025285/Tools-Tutorial-Day-Bungie-s)

## Techniques and practical checks

- **Validate a resolved configuration.** Define types, units, numeric bounds, legal enum values, and cross-field constraints. Apply the documented precedence of defaults, platform profiles, user choices, and remote values before validating the final combination. Reject nonfinite numbers where they are unsupported. **Check** valid extremes, invalid values, missing keys, and a combination where two individually valid fields conflict. Confirm the diagnostic identifies the setting and constraint and the runtime receives a valid fallback or a clear startup failure.
- **Declare scope and mutability.** Mark each setting as startup-only, session-wide, or player-local, and define the owner authorized to change it. Route accepted changes through one publication path so cached consumers can update coherently. **Check** alter each scope while a session is active and while a player leaves. Verify startup-only values wait for their documented boundary, shared settings agree across participants, and player caches release safely.
- **Publish complete revisions.** Parse and validate a candidate away from active readers. Build dependent derived values, assign a revision identifier, and switch readers to the complete candidate at a safe boundary. Keep the last valid revision available for recovery where appropriate. **Check** fail parsing, derived-value creation, and publication separately. Verify readers see either the old complete revision or the new complete revision and that the error identifies the rejected candidate.
- **Record effective values and provenance.** Expose a diagnostic view containing the applied revision, resolved values, and source layer, with sensitive credentials excluded. Keep a small compatibility fixture for settings that influence simulation or saved state. **Check** reproduce a reported issue from its configuration revision and compare editor, packaged client, and server resolutions. Verify that a changed default or platform override is visible in the trace and produces the expected behavior.
