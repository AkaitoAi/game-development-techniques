# Engine subsystem lifecycles

## Problem and design reasoning

A subsystem can expose a service before it is ready, complete an asynchronous request against an unloaded scene, or keep a worker running after shutdown. These are ownership and lifetime failures. Explicit startup, readiness, quiescence, and teardown boundaries clarify when callers may use a subsystem and what can outlive its current session.

The shipped *Quake III Arena* source exposes explicit game-module initialize and shutdown commands through the same entry point that receives frame commands. Bungie's GDC talks on *Destiny* describe a migration in which application lifecycle code temporarily had to handle both legacy maps and new environments, and a resource tracker designed to validate that reads, writes, creations, and destructions occur at safe times in its job-based frame. The transferable inference is to declare each subsystem's dependencies and make asynchronous lifetime boundaries observable during development. ## Techniques and practical checks

- **Give services an explicit owner and readiness condition.** Mark each dependency as process-, session-, or world-scoped. Declare which services must be ready before publishing an interface and how optional features report unavailability. **Check** a cold start with the slowest dependency delayed and an optional dependency absent. Verify that callers either wait or receive the expected fallback.
- **Unwind partial startup.** Track which acquisitions completed successfully. On failure, clean up those acquisitions in reverse dependency order and allow retry only after returning to a known state. **Check** fault injection after each acquisition in a development fixture. Retry initialization and verify that handles and subscriptions return to their expected counts.
- **Quiesce work before releasing dependencies.** Stop admitting requests, cancel or drain owned work, and observe the relevant completion fence before freeing resources. Carry a world or session generation identifier across asynchronous boundaries where old completions could otherwise reach a replacement. **Check** an unload followed immediately by reload while a test job is blocked. Release the job and verify that its completion cannot mutate the replacement world.
- **Test repeated lifecycle boundaries.** Instrument the active subsystem state and counts of owned tasks, handles, and allocations. Exercise restart in the same process as well as full exit. **Check** many world or session reloads, plus shutdown while work is in flight. Verify counts return to baseline for the appropriate lifetime and that each shutdown completes within the measured budget.
