# Data-driven gameplay authoring

## Problem and design reasoning

When each ability, recipe, or item variation is hard-coded, small tuning changes require code edits and new behavior can bypass shared rules. In *For Honor*, Ubisoft built a modifiers system so designers could author effects that change gameplay values and properties. In *Factorio*, Wube documents a prototype stage that loads content definitions ahead of runtime and validates their format when the engine consumes them. The design inference is to expose safe parameters and composition rules in data while keeping the execution semantics and validation in code. [GDC 2017, Modify Everything! Data-Driven Gameplay Effects on For Honor](https://media.gdcvault.com/gdc2017/Presentations/LeChevalier_Aurelie_ModifyEverythingData.pdf) · [Wube prototype data lifecycle](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html) · [Wube prototype data validation](https://lua-api.factorio.com/latest/types/Data.html)

## Techniques and practical checks

- **Separate definitions from instances.** Use immutable definitions with stable IDs for authored properties. Store mutable state such as charges, ownership, and expiry on each runtime instance. **Check** two actors holding items with the same definition, then mutate one item's charges and reload. Verify the other actor and the authored asset remain unchanged.
- **Validate during content import or build.** Specify units, ranges, defaults, and legal references. Resolve IDs and check graph constraints, such as prerequisite cycles or an effect pointing to a missing asset. Publish diagnostics with the relevant asset and field. **Check** a duplicate ID, missing reference, invalid duration, and dependency cycle. Verify each fails before the content ships and the error locates the source.
- **Make composition outcomes inspectable.** Use a bounded vocabulary of operations with defined ordering, stacking, and conflict rules. Show resolved values and their source definitions in a preview or trace. **Check** two modifiers acting on the same value and change their asset order. Verify that the preview and packaged build produce the same result according to the precedence rule.
- **Version content across builds.** Record the schema version and identify the content revision used by the runtime. Preserve IDs across renames and define migrations or explicit handling for removed definitions. Apply a reload at a safe boundary if live editing is supported. **Check** an old save containing a renamed item and a removed item, plus a partial reload failure. Verify migration is repeatable and a rejected update leaves the last valid definitions usable.
